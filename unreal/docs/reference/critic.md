## 1. Resolved facts (single agreed values for the build)

1. **Engine: Unreal Engine 5.8.x.** `XRCampus.uproject` → `"EngineAssociation": "5.8"`. Install the newest 5.8.x the Epic Games Launcher offers (the reports say 5.8.3, 22 Sep 2026 — secondary source, not re-verified). No 5.9 preview is known; the PixelStreaming infrastructure repo has `UE5.8` (updated 2026-10-14), `UE5.7`, `UE5.6` branches and **no `UE5.9`** [github]. `assets.md` said "5.7/5.8" — corrected to 5.8 (its header values were read from 5.7 headers, which is fine: every key it uses also exists in 5.8 inis).
2. **The user's machine is unknown** (OS and GPU). `assets.md` §intro claimed "the research preflight recorded the user's Mac as an M5 Max on macOS 26.5.1" — **false attribution**: that sentence comes from `research/dl/ue58traps.md` §6 / `toolkit-map.md`, which are a downloaded third-party skill (scenario-labs) describing *their* author's Mac on 2026-09-24. The runbook must start with a preflight that detects OS/GPU and picks a profile (§4 G2).
3. **Platform capability matrix to plan against** (agreed across render/automation/traps; delivery.md's "not supported on Mac" line came from an older Epic page):
   - Windows 11 + DX12 SM6 + RTX / RX 6000+ → full stack (Lumen HWRT + Hit Lighting for Reflections, MegaLights, Nanite, VSM, Substrate Adaptive, Path Tracer).
   - Windows without DXR → Lumen SWRT, VSM, Nanite, Substrate; MegaLights/Path Tracer off.
   - Apple Silicon **M2+** → Nanite + VSM (Beta), Lumen SWRT, TSR; Lumen HWRT and MegaLights **Experimental at best — never a dependency**; Path Tracer only with macOS ≥ 26.4 (5.8).
   - Apple Silicon M1 → Lumen SWRT only, no Nanite/VSM.
   - Intel Mac → no rendering support in 5.8 (cook/headless only).
   - Linux (Vulkan SM6) → full stack; the cheaper pixel-streaming host.
4. **Mac toolchain** (newest Epic page revision, saved 2026-09-24 by the third-party KB; delivery.md's Sonoma 14.0 / Xcode 15.2 is from an older revision): macOS 14.5+ (26.4+ for Path Tracer), **Xcode 26.0 minimum, 26.1.x recommended, 26.4 flagged incompatible**; the 5.8 SDK table disagrees → runbook verifies on the machine. C++ project ⇒ Xcode required; Blueprint-only would not.
5. **Windows toolchain**: Visual Studio 2026 Community (18.x, MSVC 14.50) is what Epic's own 2026 EOS sample `.vsconfig` requests [github, saved in `research/dl/eos.vsconfig`]; the VS 2026 component directory confirms `Microsoft.VisualStudio.Workload.NativeGame`, `Component.Unreal.Ide`, `Component.Unreal.Debugger`, `Microsoft.Net.Component.4.6.2.TargetingPack` [P, MS Learn]. MS Learn also states VS Tools for Unreal supports VS 2022 17.7+ and UE 5.0+ [P]. Whether UE 5.8's UBT still accepts VS 2022 is **unverified** (Epic page blocked) → runbook: read Epic's "Setting Up Visual Studio" (5.8) on the machine; default to VS 2026.
6. **Cowork execution model (verified on support.claude.com):** since 6 October (2026) Cowork sessions run code in a **cloud sandbox on Anthropic's servers**; there is no "only on your computer" option for new sessions. A cloud session reaches the user's computer **only through the open Claude Desktop app**, limited to **connected folders**, each local tool call permission-checked. "Local connectors and plugins that include local MCP servers work through the desktop app only" (i.e. they run on the device, not in the sandbox — must be tested on day 1 with the Desktop Commander plugin). **Computer use**: Pro/Max only, beta, macOS + Windows, asks per application, computer must stay awake. **Claude Code** installs natively on macOS/Linux/WSL (curl) and Windows (PowerShell) or `brew install --cask claude-code`, runs commands on the host and asks before each command/edit. ⇒ **Primary host executor = Claude Code on the user's machine**, driven by the runbook; Cowork orchestrates through the connected project folder; computer use covers the GUI-only steps (Epic Games Launcher sign-in + 5.8 install, VS/Xcode installer prompts, MetaHuman Creator cloud steps).
7. **Coordinate conversion (verified numerically from `layout.json`):** `UE_X = 100·x`, `UE_Y = 100·z`, `UE_Z = 100·y`; `UE_yaw° = (−90 − deg(yaw)) mod 360` (identical to content.md's `atan2(−cos yaw, −sin yaw)` form — checked at 0, ±π/2, π, −0.41); `UE_pitch° = deg(pitch)`; sun `SUN_DIR=[40,62,30]` → DirectionalLight rotator **(pitch −51.1°, yaw −143.1°, roll 0)** recomputed and matching; spawn (0, −70, 0) cm, yaw −90°; Margaret facing yaw 101.64° recomputed from `faces_m`. Handedness argument (det −1 swap) is correct. The Blender→UE **FBX** route provably yields this map (Blender (x,−z,y) → FBX (x, y, z)_Y-up → UE (x, z, y)). The **Interchange glTF** route is expected to give the same map (UE's GLTF conversion swaps Y/Z and negates the quaternion W — critic's recollection of `GLTFCore`, not re-verified); the specs' single-landmark import test (library door at UE X=−1200, Y −460..−140, Z 0..340; arched window X=−3200; token `t-museum` at (−535, −4135, 36) cm) is the gate. If text reads mirrored, use the FBX route for the Blender assets and re-export the greybox with the axis swap applied in the exporter — do not touch `layout.json`.

9. **Naming contract (resolves content.md vs systems.md):** C++ structs use the `FXR` prefix, the view struct is **`FXRView {FVector Location; float Yaw; float Pitch;}`** (not `FCampusView`), rows are `FXR<Name>Row : FTableRowBase`.
